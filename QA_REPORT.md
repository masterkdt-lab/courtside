Observations (not failures; for KC and the orchestrator to decide on):

1. Revoking or pausing a code does not evict an existing session from viewing `/site`: the guard is cookie-only (per plan 4.0), so a guest who entered before the change can still browse for up to 30 days. `POST /api/request` blocks `revoked` but not `paused` (the plan only specifies the gate behaviour for paused). If that matters, re-check the invite in `lib/guard.js` or in `api/request.js`.
2. The double-submit guard keys on invite code + type + weeks only (plan 4.0). A guest who changes room or add-ons and sends again within 60 seconds gets the first request's ID and no new row. Plan-conformant; worth a line in the README if it surprises Katie.
3. The 60-second trips cache is per server instance; on Vercel each warm function instance has its own, so "within a minute" holds per instance.
4. Dev server returns 404 for `/index.html` and `/privacy.html`, where Vercel's `cleanUrls` would redirect to `/` and `/privacy`. `/site.html` is handled. Local-only difference, no plan requirement.
5. Chromium prints "Failed to load resource: … 401/409" to the console for any non-2xx `fetch` (a wrong code, a closed week). These are the browser's own lines, not script errors; the e2e suite lists them separately and asserts there are none on plain page loads.

## Orchestrator follow-up (after this report)

Two observations above were tightened after QA signed off, with unit tests added in `tests/api.request.test.js`:

1. A code set to `paused` after sign-in is now refused at request time with 401, the same as `revoked`. Viewing `/site` on an existing cookie is still allowed until the cookie expires; the guard does not consult the Sheet.
2. The double-submit guard now keys on code + type + weeks + brief, so a request the guest edited within 60 seconds creates a new row, while a true double submit still collapses to one.
